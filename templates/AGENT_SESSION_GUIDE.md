# 에이전트 세션 운용 가이드

> Claude Code 같은 AI 에이전트로 개발할 때 **컨텍스트(토큰) 폭증을 막고**, 세션을 공학적으로 운용하기 위한 가이드입니다.  
> Blueprint Framework의 문서들(SPEC.md · AGENT_STATE.md · 폴더 README)이 이 전략을 어떻게 뒷받침하는지 함께 설명합니다.

> **핵심 전제**: 에이전트는 공학적 판단을 대신하는 도구가 아닙니다. 명세가 확정된 범위 안에서 구현을 수행하는 실행 도구입니다.  
> 설계·우선순위·세션 분리는 개발자가 담당합니다.

---

## 1. 왜 컨텍스트가 폭증하는가

| 원인 | 설명 | 프레임워크의 대응 |
|------|------|------------------|
| **반복 수정 누적** | 실패 후 재시도를 같은 대화에서 반복하면 실패 기록이 모두 컨텍스트로 쌓임 | 세션 분리 + `AGENT_STATE.md` 인계 |
| **대화 기록 재처리** | 대화가 길어질수록 매 응답마다 처리할 기록이 커짐 | 한 세션 = 한 기능 ID |
| **범위 미확정 작업** | 목표가 불명확하면 방향 탐색과 수정 반복에 토큰을 소모 | `SPEC.md` 수용 기준 |
| **불필요한 파일 읽기** | 전체 문서·코드를 매번 읽음 | 기능 ID 블록 단위 읽기, 폴더 README 단위 컨텍스트 |

> 요금제별 사용 한도와 가격은 자주 바뀌므로 이 문서에 적지 않습니다.  
> 최신 정보는 [Claude 도움말 센터](https://support.claude.com)의 요금제·사용 한도 안내에서 확인하세요.

## 2. 세션 운용 전략 — 5단계

### STEP 1. 코딩 전에 명세를 확정한다

에이전트에게 탐색 여지를 주지 않고 명확한 목표를 전달합니다.

- `SPEC.md`에 기능 목록(F-ID)과 **수용 기준**을 먼저 작성합니다 → `templates/SPEC_TEMPLATE.md`
- 기술 스택·모듈 구조·설계 결정은 `ARCHITECTURE.md`에, 전역 행동 제약은 루트 `README.md` Agent Control에 둡니다 → `templates/ARCHITECTURE_TEMPLATE.md`
- 명세가 비어 있다면 코딩 세션 대신 "SPEC.md 함께 작성하기" 세션을 먼저 엽니다 → `templates/FIRST_PROMPTS.md`

### STEP 2. 기능을 원자 단위로 분해한다

**원칙: 한 세션 = 한 기능 ID**

```
❌ 잘못된 접근: "로그인, 회원가입, 피드, 프로필, 설정 화면 모두 만들어줘"

✅ 올바른 접근:
  세션 1: F-001 이메일 로그인
  세션 2: F-002 회원가입 + 이메일 인증
  세션 3: F-003 피드 리스트 (무한 스크롤, 페이지당 20개)
  세션 4: F-004 프로필 조회 + 수정
  세션 5: F-005 설정 화면
```

한 기능이 한 세션에 끝나지 않을 만큼 크다면, SPEC.md에서 기능을 더 작은 ID로 나눕니다.

### STEP 3. 기능이 끝나면 새 세션을 연다

```
[기능 완료] → Tracker ✅ · AGENT_STATE.md 갱신 · 커밋 → 새 세션 → CLAUDE.md 자동 로딩 → 다음 기능
```

**금지 행동:**
- 한 대화에서 여러 기능을 연속으로 요청
- 같은 에러를 한 세션에서 계속 반복 수정 (3회를 넘기면 새 세션으로 전환)

### STEP 4. 브리핑은 파일로 넘긴다

전체 코드나 긴 설명을 대화에 붙여넣지 않습니다.  
Blueprint Framework에서는 **`AGENT_STATE.md`가 세션 브리핑 역할**을 합니다.

| 예전 방식 (수동 브리핑) | 프레임워크 방식 |
|---|---|
| 기술 스택 · 허용 라이브러리 | `ARCHITECTURE.md` §2 (필요할 때만 읽음) |
| 완료된 기능 | 루트 `README.md` Progress Tracker |
| 지금 작업할 기능 | `AGENT_STATE.md` Current Focus |
| 제약 조건 | `AGENT_STATE.md` Active Rules · 폴더 `README.md` Agent Control |
| 파일 위치 | Tracker의 Owner Folder |
| 완료 기준 | `SPEC.md` 해당 기능의 수용 기준 |

그래서 세션 시작 프롬프트는 이것으로 충분합니다:

```
CLAUDE.md를 읽고 세션 시작 프로토콜을 실행해.
오늘 작업: F-003. 수용 기준을 읽고 구현 계획을 3줄로 요약해줘. 확인 후 코딩 시작.
```

프레임워크를 쓰지 않는 프로젝트라면 아래 수동 브리핑 템플릿을 사용하세요:

```markdown
## 프로젝트 현황
📁 기술 스택: [[ 언어 / 프레임워크 / DB ]]
✅ 완료된 기능: [[ 목록 ]]
🔧 지금 작업할 기능: [[ 단 하나의 기능 ]]
📌 제약 조건: [[ 사용 금지 라이브러리, 성능 요건 등 ]]
⚠️ 파일 위치: [[ 신규 생성 또는 수정할 파일 경로 ]]
🎯 완료 기준: [[ 이 기능이 완료되었다고 판단하는 조건 ]]

→ 위 내용을 기반으로 구현 계획을 3줄로 요약해줘. 확인 후 코딩 시작.
```

### STEP 5. 계획을 먼저 확인하고 구현한다

```
1. 브리핑 전달 → "계획 먼저 요약해줘"
2. 계획 확인 → 방향이 맞으면 "진행해줘" / 틀리면 수정 요청
3. 구현 완료 → 수용 기준 하나씩 확인
4. 완료 후 → Tracker · STATE 갱신, 새 세션 시작
```

## 3. MVP 개발 시 권장 구현 순서

```
1단계: 인증 (로그인 / 회원가입)
2단계: 핵심 데이터 모델 + DB 스키마 (SPEC.md §7)
3단계: 핵심 CRUD 기능 1개
4단계: 기본 화면 흐름 (SPEC.md §6)
5단계: 외부 연동 1개 (결제 / 푸시 알림 / 이미지 업로드 등, SPEC.md §10)
```

각 단계는 SPEC.md의 기능 ID 하나 이상에 대응해야 합니다.  
기술 스택은 팀이 익숙하고, 타입 검사가 있는 언어(TypeScript, Dart 등)를 고르면 에이전트가 오류를 스스로 잡기 쉽습니다. 선택 이유는 ARCHITECTURE.md §9 ADR에 남깁니다.

## 4. 역할 분담 원칙

| 에이전트가 잘하는 것 | 개발자가 직접 해야 하는 것 |
|---------------------|--------------------------|
| 명세 범위 내 코드 구현 | 기능 우선순위 결정 (SPEC.md §4.1) |
| 에러 메시지 분석 및 수정 | 세션 분리 타이밍 판단 |
| 보일러플레이트 생성 | 수용 기준 정의 (SPEC.md §4.2) |
| 리팩터링, 타입 정의 | 기술 스택 선택 (ARCHITECTURE.md §2 · §9) |
| 테스트 코드 작성 | 아키텍처 방향 결정 (ARCHITECTURE.md · DFD · Agent Control) |

## 5. 토큰 절약 체크리스트

세션 시작 전:
- [ ] 이번 세션에서 구현할 기능 ID가 **단 하나**로 확정되었는가?
- [ ] 그 기능의 수용 기준이 SPEC.md에 있는가?
- [ ] `AGENT_STATE.md` Current Focus가 최신인가?

세션 진행 중:
- [ ] 에이전트에게 계획 요약을 먼저 요청했는가?
- [ ] 전체 코드 파일을 대화에 붙여넣지 않았는가?
- [ ] 같은 에러를 한 세션에서 3회 넘게 반복하지 않았는가?

세션 종료 후:
- [ ] 수용 기준을 모두 확인하고 Tracker를 갱신했는가?
- [ ] `AGENT_STATE.md` 세션 로그와 Current Focus를 갱신했는가?
- [ ] 커밋했는가?

## 6. 자주 발생하는 실수와 대응

| 실수 | 증상 | 대응 |
|------|------|------|
| 한 세션에서 너무 많은 기능 요청 | 사용 한도 임박, 응답 품질 저하 | 기능 ID 단위로 새 세션 시작 |
| 전체 코드 파일 붙여넣기 | 즉시 토큰 급증 | 파일 경로와 변경 부분만 전달 |
| 에러 반복 수정 무한 루프 | 같은 에러가 계속 반복됨 | 새 세션에서 에러 메시지만 요약해 전달 |
| 완료 기준 없이 "더 잘 만들어줘" | 방향 없는 반복 수정 | SPEC.md 수용 기준 작성 후 재요청 |
| 아키텍처 결정을 에이전트에게 위임 | 일관성 없는 코드 구조 | 구조는 개발자가 결정(ARCHITECTURE.md ADR), 에이전트는 제안만 |

## 7. 세션 운용 흐름도

```
[새 세션 시작] ── CLAUDE.md 자동 로딩 → AGENT_STATE.md 읽기
     │
     ▼
[기능 ID 지정] ── SPEC.md 해당 블록 + Owner Folder README 읽기
     │
     ▼
[에이전트: 계획 3줄 요약]
     │
     ▼
[개발자: 계획 확인]──── 수정 필요 ──→ [계획 수정 요청] ──→ 재확인
     │
   승인
     │
     ▼
[에이전트: 코드 구현]
     │
     ▼
[수용 기준 확인]──── 미통과 ──→ [에러 메시지만 전달, 수정 요청]
     │                                   │
   통과                          3회 초과 시 새 세션
     │
     ▼
[Tracker ✅ + AGENT_STATE.md 갱신 + 커밋]
     │
     ▼
[새 세션 시작] ← 다음 기능 ID로 반복
```
